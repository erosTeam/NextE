# 产品 Bug / Feature 工作规则

本文件负责产品语义、实现范围和用户路径验收。它不是任务队列；用户最新明确请求始终决定当前
工作，历史计划和证据只能用于定位。

## 开工前

1. 复述需要改变的结果和明确非目标，避免把问题替换成相邻问题。
2. 查当前 NextE 源码、相关提交和数据所有权；需要对标时给出 `eros_fe` 的具体文件/方法，平台
   表达再查 V2Next/HDS。
3. 写五行 grounding：参考实现、主信息、主/次动作、本轮可用闭环与非目标、HarmonyOS 表达方式。
4. 遇到会改变产品语义、数据字段/同步、信息层级或远端结构的取舍，列出收益与问题并等待用户
   决策，不通过绕过方案替用户决定。

## 实现纪律

- 修正确性回归时做改变行为的最小修复；不顺手重做 UI、parser、持久化或状态所有权。
- 设置项按用户心智归类；详情、列表、半模态、设置和管理页优先复用项目同类结构。
- 列表分页、刷新和缓存是不同层：查询必须有界，UI 增量加载，刷新保留可展示内容，失败不清空。
- 用户可见数据字段必须统一定义其语义、来源、存储、同步和展示位置；不能为了避开迁移而生成
  只在单设备成立的镜像/替代字段。
- EH 远端写入、账号和 Cookie 操作遵循 [EH integration contract](../eh-integration-contract.md)。

## 验收

- 先写一条真实用户路径：从哪里进入、做什么、状态如何变化、最终看到什么。
- 同时列出最容易坏的反例状态，例如加载中、空数据、缓存命中、长文本、小屏/折叠屏、键盘打开、
  滚动后、弹层切换或失败重试；选择与当前改动有关的至少三项。
- 日志证明动作/请求/状态链路，截图或 layout 证明可见结果，构建证明候选可安装。三者不能互相
  冒充。
- 没有运行时证据时写 `implemented candidate / needs QA`；已复现但仍失败写 `reopened / failed QA`；
  只有对应用户路径通过后才写 `accepted` 或 `completed`。
- 远端写入、资源消耗和不可逆动作默认验证到确认框或本地无害边界；真正提交必须有用户明确授权。

### 视觉证据判读门禁

这是一项基于画面作出判断的责任，不得替换成正则、截图数量或机械打勾。每次用截图或录屏支持
“通过”结论前，必须执行以下判读：

- 先用自然语言写出本次画面必须成立的完整关系，不只写被修改的目标元素。转场至少包含：源页面
  的完整背景和其他内容、运动元素的位置/尺寸/形状、目标页面内容、动画结束前后的真实组件交接，
  以及不应受影响的标题栏、系统栏和相邻元素。用户明确指出的区域自动成为必查区域，不能换成
  更容易观察的相邻对象。
- 第一遍只按时间顺序看原始画面，不以源码、日志、预期机制或“代码已经这样处理”解释异常。连续
  录屏必须检查完整动作区间；联系表只能定位可疑帧，不能代替对原分辨率帧和实际视频的判读。
- 判读前先核对稳定设备别名/型号、折叠状态、方向和该状态的实际窗口/显示像素尺寸。HDC target/IP
  不是证据身份；状态不完整的样本只能保留为视觉线索，不能和另一状态的布局或帧做坐标、缩放比例、
  落点或形状的定量映射。一次录屏内发生旋转、折叠/展开或窗口尺寸变化时，按动作顺序分别记录每个
  状态检查点，并只在明确对应的状态内比较几何。
- 画面中每个消失、遮挡、跳变、错位、变形、重排、闪烁、颜色/圆角突变和背景缺失，都必须留下
  明确结论：由用户要求或已接受参考证明为预期，或者判为失败。来源不明、无法解释、只因实现者
  认为“应该如此”的现象不得略过，也不得记为通过。
- 第二遍专门做交接核对：比较运动层最后可见帧与真实组件恢复后的第一帧，并比较动画开始前与返程
  结束后的完整页面。涉及位置、尺寸或形状时，使用原始帧叠加、像素差异或当前布局边界验证；
  “看起来接近”“飞到了附近”不成立。
- 验收报告必须同时说明完整场景、运动主体和最终交接的观察结果，并给出可复查的录屏路径与关键
  帧范围。只报告帧数、哈希、构建结果或某几张支持结论的截图，视为没有完成视觉判读。
- 任意一个可见反例都会否决该候选及其所有宽泛“已修复”结论；其他帧或其他场景通过不能投票抵消。
  用户随后从同一证据指出反例时，立即撤销原通过结论，把该样本标为 `failed QA`，先重新判读原证据，
  不得继续用原结论指导修补。

## 记录与生命周期

- 非平凡任务可在 `docs/plans/active/` 建一个当前计划；计划只记录当前范围、关键证据、未决项和
  完成判据，不建立跨任务调度队列。
- 实现完成且验证闭环后移到 `docs/plans/completed/`；被替代、长期停用、仅供查证或未接受但不再
  活跃的材料移到 `docs/plans/archive/`。
- 不维护全局追加式 grounding/事故/dispatch 账本。需要长期生效的规则合并到对应 agent guide；
  单次证据留在任务计划或 Git 历史。
